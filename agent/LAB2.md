# Лабораторная работа №2. Агент с доступом к LLM

Консольный Python-агент в каталоге `agent/`, который обращается к языковой модели
через OpenAI-совместимый API. Провайдер — RouterAI (`https://routerai.ru/api/v1`),
модель по умолчанию — `deepseek/deepseek-v4-flash`. Ключ и настройки читаются
из `agent/.env` (шаблон — `agent/.env.example`, сам `.env` в git не попадает).

Запуск:

```bash
cd agent
pip install -r requirements.txt
python agent.py          # интерактивный чат с инструментами
python agent.py --once   # один запрос без истории (проверка шага 1)
```

Агент работает с файлами в `agent/workspace/` (папка исключена из git).

не должны попадать в git; библиотеки `openai` и `python-dotenv` — зафиксировать

- `agent/requirements.txt`: `openai==3.37.0`, `python-dotenv==1.0.1`;
- `agent/.env.example` — шаблон настроек (`ROUTERAI_API_KEY`, `BASE_URL`, `MODEL`,

## Шаг 1. Первый запрос к модели

**Задание.** Вызвать модель одним запросом без инструментов и напечатать три вещи:
`message.content`, `finish_reason` и `usage`. Проверка: на вопрос «Что такое токен?»
приходит ответ, `finish_reason = stop`, видны числа входных и выходных токенов.

**Сделано.**

- функция `run_once()`: запрос `chat.completions.create` с одним сообщением
  пользователя, без `tools` и `tool_choice`;
- печать трёх требуемых блоков: текст ответа, причина завершения, `prompt_tokens` /
  `completion_tokens` / `total_tokens`;
- проверка `finish_reason == "stop"` (иначе код возврата 1);
- обработка ошибок API: 401 (ключ), 402 (баланс), 403 (региональная блокировка
  OpenRouter), а также «пустых» ответов, когда провайдер отдаёт HTTP 200
  с телом-ошибкой вместо `choices`.

**Проверка.** `python agent.py --once` → ответ на вопрос про токен,
`finish_reason: stop`, `prompt_tokens: 9`, `completion_tokens: 1117`,
`total_tokens: 1126`.

## Шаг 2. Чат с историей

**Задание.** Сделать цикл `input()`: каждый вопрос и ответ добавлять в список
`messages`, первым идёт системный промпт.

**Сделано.**

- `run_chat()` — цикл `input("Вы: ")`; история хранится в одном списке `messages`,
  первым элементом которого всегда идёт `{"role": "system", "content": ...}`
  (текст задаётся переменной `SYSTEM_PROMPT`, есть значение по умолчанию);
- вопрос добавляется в историю как `{"role": "user"}`, ответ модели —
  как `{"role": "assistant"}`; на каждом шаге в API уходит **весь** список,
  поэтому модель помнит предыдущие реплики;
- после каждой реплики печатается `usage`, `finish_reason` и текущий размер истории;
- команды: `/reset` (`/clear`) — очистить историю, оставив системный промпт;
  `/exit`, `/quit`, `exit`, `quit`, Ctrl+D, Ctrl+C — выход; пустой ввод игнорируется;
- если запрос завершился ошибкой, вопрос убирается из истории, чтобы она
  не рассинхронизировалась.

**Проверка.** Диалог из двух связанных вопросов: второй ответ учитывает первый,
`prompt_tokens` растёт (42 → 152), в истории 3 → 5 сообщений. После `/reset`
модель уже не помнит имя, названное до сброса (`prompt_tokens` снова 37).

## Шаг 3. Инструменты и агентный цикл

**Задание.** Реализовать две функции по комментариям TODO:

1. `execute_tool(name, raw_args)` — разобрать JSON-аргументы, вызвать функцию,
   любую ошибку вернуть строкой `ОШИБКА: …`, а не исключением;
2. `run_agent(messages)` — цикл не длиннее `MAX_STEPS`: запрос с `tools` →
   сохранить ответ ассистента → если нет `tool_calls`, вернуть текст → иначе
   выполнить каждый вызов и добавить `{"role": "tool", "tool_call_id": …, "content": …}`.

Печатать на каждом шаге имя вызванного инструмента, аргументы и `usage`.

**Сделано.**

- инструменты `list_files(path=".")` и `read_file(path)` + их описания в `TOOLS`
  (формат function calling). Оба работают только внутри `agent/workspace/`:
  путь вида `../../.env` или абсолютный путь вне папки отклоняется;
- `execute_tool(name, raw_args)`:
  - пустые аргументы трактуются как `{}`, битый JSON → `ОШИБКА: не удалось
    разобрать аргументы JSON (…)`;
  - аргументы не объект → `ОШИБКА: аргументы должны быть JSON-объектом …`;
  - неизвестный инструмент → `ОШИБКА: неизвестный инструмент '…'. Доступны: …`;
  - `TypeError` (нет обязательного аргумента, лишний аргумент) и любые
    исключения функций → `ОШИБКА: <Тип>: <текст>`;
  - длинные результаты обрезаются (`MAX_ITEMS`, `MAX_FILE_CHARS`), чтобы
    не раздувать контекст;
- `run_agent(messages, max_steps)`: цикл до `MAX_STEPS` (по умолчанию 8,
  переопределяется переменной `MAX_STEPS`); ответ ассистента сохраняется
  в историю целиком (`message.model_dump`), поэтому связка «вызов → результат»
  не теряется; результаты инструментов добавляются сообщениями с ролью `tool`
  и `tool_call_id`; при отсутствии `tool_calls` возвращается текст ответа;
  по исчерпании лимита печатается предупреждение и возвращается сообщение
  об остановке;
- логирование на каждом шаге, например:

  ```
  [шаг 1/8] usage: prompt=489 completion=61 total=550 finish_reason=tool_calls
  [шаг 1] инструмент: list_files | аргументы: {}
  [шаг 1] результат list_files: metrics.json readme.txt
  ```

- чат из шага 2 теперь отвечает через `run_agent`, поэтому история включает
  и вызовы инструментов, и их результаты.

**Проверка.**

- запрос «посмотри файлы и прочитай metrics.json» → 3 шага: `list_files` →
  `read_file {"path": "metrics.json"}` → текстовый ответ с CPU 34% и 54 °C,
  `finish_reason=tool_calls`, `tool_calls`, затем `stop`;
- обращение к несуществующему файлу: инструмент вернул
  `ОШИБКА: FileNotFoundError: файл не найден: missing.txt`, агент не упал и
  на следующем шаге сообщил, что файла нет;
- лимит шагов (`MAX_STEPS=1`): после одного вызова агент останавливается
  с сообщением «Не удалось завершить задачу за 1 шагов…»;
- `execute_tool` отдельно: 12 случаев (валидные вызовы, битый JSON, пустые
  аргументы, неизвестный инструмент, отсутствующий/лишний аргумент,
  несуществующий файл, папка вместо файла, выход за пределы рабочей папки,
  аргументы-список) — все вернули строку, ни одного исключения.

## Шаг 4. Запись с подтверждением

**Задание.** Добавить в `TOOLS` описание `write_file` (параметры `path` и
`content`, оба обязательные). Реализация с запросом «Разрешить? [y/N]» уже есть —
разобраться, что модель получает при отказе.

**Сделано.**

- в `TOOLS` добавлен `write_file` с `required: ["path", "content"]`; в описании
  прямо сказано, что инструмент меняет файловую систему и требует
  подтверждения пользователя;
- `write_file(path, content)` перед записью печатает, что произойдёт
  (создание или перезапись), текущий размер файла, новый размер и первые
  10 строк содержимого, затем спрашивает `Разрешить? [y/N]`;
- согласием считается только явное `y` / `yes` / `д` / `да`; `Enter`, `n`,
  `Ctrl+D` и `Ctrl+C` — отказ. Проверка пути выполняется **до** вопроса,
  поэтому попытка записать `../evil.txt` или `C:/Windows/temp.txt` отклоняется
  без интерактивного запроса;
- результат всегда строка: `OK: файл '...' создан (N символов).` /
  `OK: файл '...' перезаписан (N символов).` при согласии и
  `ОТКАЗ: пользователь не разрешил запись файла '...'. Файл не изменён.`
  при отказе.

**Что модель получает при отказе.**

Модель не видит сам диалог подтверждения — в историю уходит обычное сообщение
с ролью `tool`, где в `content` лежит текст отказа. При `AGENT_DEBUG=1` это
видно дословно:

```
{"role": "tool", "tool_call_id": "call_7861f54a68354a1ab66651e0",
 "content": "ОТКАЗ: пользователь не разрешил запись файла 'note.txt'. Файл не изменён."}
```

То есть отказ — это **не исключение и не ошибка API**, а нормальный результат
инструмента, такой же, как список файлов или содержимое файла. Ничего не
выбрасывается: `write_file` не пишет файл и возвращает строку, `run_agent`
кладёт её в `messages`, и на следующем шаге модель читает её как факт.

Дальше поведение зависит от модели, но в проверке оно было предсказуемым:
`deepseek/deepseek-v4-flash` не повторяет вызов автоматически (иначе получился
бы бесконечный цикл «спросить — отказ — спросить»), а сообщает пользователю,
что запись не выполнена, и предлагает повторить при необходимости:

```
Агент: Пользователь отклонил запись. Файл `note.txt` **не был изменён**.
Если хотите, попробуйте ещё раз — я готов выполнить перезапись после
вашего подтверждения.
```

Формулировка «ОТКАЗ: …» выбрана намеренно: это не сбой инструмента, а решение
пользователя, поэтому префикс `ОШИБКА:` здесь не подходит — он означал бы
«инструмент сломался» и подталкивал бы модель к повторным попыткам.
Файл при отказе действительно остаётся прежним: `note.txt` сохранил содержимое
`CPU 34%, RAM 62%`, хотя модель просила записать `CPU 99%`.

**Проверка.**

- согласие (`y`): файл создан, содержимое на диске совпадает с аргументом
  (`note.txt = 'CPU 34%, RAM 62%.'`), модель отвечает «Файл создан»;
- отказ (`n`) и отказ по умолчанию (`Enter`): на диске по-прежнему старое
  содержимое, модель сообщает, что файл не изменён; `finish_reason=stop`,
  повторных `tool_calls` нет;
- прямой вызов `execute_tool` с `write_file`: `../evil.txt` и
  `C:/Windows/temp.txt` → `ОШИБКА: ValueError: путь вне рабочей папки: …`;
  `.` → `ОШИБКА: IsADirectoryError: это папка, записать файл нельзя: .`;
  без `content` → `ОШИБКА: неверные аргументы для write_file: …`;
  битый JSON → `ОШИБКА: не удалось разобрать аргументы JSON (…)`;
- `write_file` без подтверждения не выполняется никогда: перед записью всегда
  печатается запрос, а проверка пути и аргументов идёт раньше него.

## Примечания

- Из России OpenRouter отдаёт `403 Access denied by security policy` независимо
  от ключа, поэтому провайдер заменён на RouterAI: достаточно поменять `BASE_URL`
  и ключ, код обращения к модели не меняется.
- Часть моделей у провайдера недоступна из региона (`google/gemini-2.5-flash-lite`
  возвращает запрет по Terms of Service), поэтому по умолчанию выбран
  `deepseek/deepseek-v4-flash`.
- Секреты хранятся только в `agent/.env`; в репозиторий попадает лишь
  `.env.example` с заглушкой вместо ключа.
